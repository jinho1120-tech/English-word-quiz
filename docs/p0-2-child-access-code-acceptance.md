# P0-2 자녀 접속코드 보안 강화 — 운영 및 수락 테스트

이 문서는 `security/p0-2-child-access-code-hardening` 구현의 배포 전 확인 절차다.

## 배포 전제

1. Vercel Production과 Preview에 `CHILD_ACCESS_CODE_PEPPER`를 각각 동일한 32자 이상 랜덤 값으로 등록한다. 예: `openssl rand -base64 32`.
2. pepper는 비밀번호 관리자 등 안전한 별도 장소에 백업한다. pepper를 잃거나 바꾸면 기존 v2 접속코드가 검증되지 않는다.
3. 먼저 코드만 배포한다. 이 릴리스는 v2와 레거시 SHA-256 해시를 모두 조회한다.
4. 배포가 정상 동작하는 것을 확인한 후 운영자가 DB 백업/복원 지점을 만든다.
5. 운영자가 직접 `DATABASE_URL`과 `CHILD_ACCESS_CODE_PEPPER`를 지정해 `node scripts/upgrade-access-code-hashes.mjs`를 실행한다. 이 저장소의 CI나 배포 작업은 운영 DB 변환을 실행하지 않는다.
6. `SELECT COUNT(*) FROM child_profiles WHERE access_code_hash NOT LIKE 'v2:%'` 결과가 0인지 확인하고, 기존 코드와 신규 코드로 로그인을 검증한다.
7. 검증을 마친 뒤 Vercel Production/Preview에 `ACCEPT_LEGACY_ACCESS_CODE_HASH=false`를 설정한다. 레거시 조회 코드 제거는 별도 후속 PR에서 한다.

**금지:** 코드 배포 전에 변환 스크립트를 실행하지 않는다. 기존 앱은 v2 해시를 조회하지 못해 자녀 로그인이 실패한다.

## 자동화 및 CI 검증

현재 저장소에는 DB 통합 테스트 러너와 격리된 테스트 DB fixture가 없다. 따라서 운영 데이터나 공유 DB를 대상으로 한 수락 테스트를 자동 실행하지 않는다. PR CI의 TypeScript 검사, 디자인 시스템 검사, Drizzle 이력 검사, Next.js 빌드 결과와 아래의 별도 스테이징 검증을 구분해서 보고한다.

## 스테이징 수락 테스트

- [ ] 같은 IP에서 잘못된 코드 10회 후 11번째 요청은 `rate_limited`이며 대기 시간을 반환한다.
- [ ] 동시 잘못된 요청 20개를 보내도 DB advisory lock 기준으로 허용 예약이 단기 한도 10개를 넘지 않는다.
- [ ] 올바른 코드로 순차 로그인 20회를 해도 성공할 때마다 해당 요청의 두 예약이 삭제되어 제한에 걸리지 않는다.
- [ ] 존재하지 않는 코드와 비활성 프로필 코드는 동일한 `invalid` 결과를 반환한다.
- [ ] 신규 발급 코드(v2)와 변환 전 레거시 코드 모두 전환 기간에 로그인된다.
- [ ] 변환 스크립트 후 기존 코드 로그인이 계속되고, 스크립트를 다시 실행해도 변경 행 수가 0이다.
- [ ] `ACCEPT_LEGACY_ACCESS_CODE_HASH=false`일 때 미변환 레거시 해시는 거부되고 v2 해시는 허용된다.
- [ ] 다른 pepper로 만든 해시 조회는 실패하며, Production에서 pepper가 없으면 호출 시점에 오류가 난다.
- [ ] `rate_limits.user_id`에는 원본 IP가 아니라 HMAC 키만 저장된다.
- [ ] 같은 IPv6 /64의 주소는 같은 키, 다른 /64는 다른 키를 만든다.
- [ ] `x-real-ip`가 없으면 `x-forwarded-for` 첫 IP를 사용한다.
- [ ] 로그인과 QR 등록의 action prefix가 달라 각각 독립적으로 제한된다.
- [ ] 코드 재발급은 v2 코드를 발급하고 기존 기기 세션을 취소하지 않는다.
- [ ] 코드 해시 유니크 충돌 시 발급을 최대 3회 재시도한다.
- [ ] 로그인 실패 10분 누적 500건에서 구조화 로그가 한 번 기록된다.

## 제한 구현 메모

요청별 예약은 `rate_limits` 기존 테이블에 UUID가 포함된 action 행으로 기록하고, 성공 시 해당 요청 행만 삭제한다. 이 방식은 환불이 다른 동시 요청의 실패 카운트를 깎는 문제를 막으며 스키마 변경이 없다. IP 원문은 저장하지 않는다. 고정 윈도우에서 한도에 가까운 순간 여러 요청이 동시에 들어오면 성공 여부가 확인되기 전 예약이 한도를 차지할 수 있으므로, 동시 성공 로그인 20회 테스트는 순차 요청으로 수행하고 동시성 테스트는 초과 실패 예약이 차단되는지 확인한다.

QR 등록 실패는 링크의 유효/존재 여부를 구분하지 않고 만료/사용 완료 문구로 반환한다. 접속코드 로그인은 존재 여부와 비활성 여부를 동일한 `invalid`로 반환한다.
